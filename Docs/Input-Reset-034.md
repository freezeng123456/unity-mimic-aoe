# 设备复位与按住输入契约 · 034

这是 P 项目输入规则；不宣称对应原作实现。实施前已用真实 InputSystem.ResetDevice 与原生日志区分设备状态、游戏边缘缓存、应用焦点和最终操作。旧运行时冻结七例4/7：A、Escape、UGUI鼠标按钮在复位后无额外释放事件时，首次新按下被旧缓存吞掉。测试sha256为5e8329d4f64fb15337f33ed237dbacafe1d493054778486b3523b2cbabdb67b6。它们是设备接口复现，不能代替完整原生失焦链。

Input System 1.20 的 `ResetDevice` 直接更新设备状态和状态监视器，不经过项目监听的 `onEvent` 路径。本轮在复位通知处按设备同步默认按钮状态、清理该设备尚未消费的旧边沿，并保持键盘与鼠标缓存隔离；鼠标复位同时取消旧 UI 按压与框选捕获，后续新点击不增加额外等待。

应用失焦是不同边界：丢弃旧待处理动作；失焦前已按住或失焦期间实际观察到按住的键/按钮，直到观察到释放才允许再次触发。恢复同步再次报告这些已知按住状态时不能凭空暂停/恢复、下令或付款。正常UI清理仍只清待分发边缘/捕获，不应将物理按住改写成新按下。选择与已发世界命令依旧保留。

不盲目丢弃恢复后的首个状态事件：本机诊断已观察到focus true和设备Enabled后，没有空键盘同步事件，首个后续事件就是实际F9；若全部首事件静默同步，会引入首次按键丢失。对失焦期间按下但从未被应用观察到的物理状态，Input System普通事件没有通用来源标记；本轮不声称已全面解决所有设备同步时序。

本轮诊断客户端是基于 0.2.12 的临时加日志构建，GUID `276339a26de042219d74a2604d163dfd`，不是封存的 0.2.12 发布二进制。它记录了最小化后的 focus false、键鼠禁用、恢复后的 focus true、F9 截图和 Escape 主动恢复，但不能替代最终 0.2.13 客户端的 OS focus 验证。桌面白色截图与客户端自身正常截图并存，不能据此推断游戏停止渲染或窗口显示问题已修复。

最终 0.2.13 构建回执为 Build GUID `ae1dace836c84d79b94d291667478592`；EditMode 110/110、PlayMode 129/129，冻结 reset/focus 用例 7/10 → 10/10，隔离用例 4/4。CLI 样本在 `65.399570` 模拟秒失焦，Finder 样本在 `20.100040` 模拟秒失焦；两个样本均未完成恢复窗口后的成功操作链。故本契约已由自动化测试和 device reset seam 支持，真实 macOS focus 恢复不能只由这些测试判定。最终正常玩家局另外记录了三次失焦后 Escape 恢复及后续经营、战斗、结算，但上述两次失败没有被抹去；精确成功/失败范围见 [Native-Verification-034.md](Native-Verification-034.md)。
