# Input reset / focus recovery review (033)

Read-only review of `DiscreteInputBuffer`, `RtsInput.OnApplicationFocus`, and `FocusPauseTests`. No source changes or native launch.

`DiscreteInputBuffer.Clear()` only executes `edges.Clear()`. It intentionally leaves `keyDown[]`, `leftDown`, `rightDown`, modifier state, and the remembered pointer position unchanged. `Capture` compares each incoming state event against those remembered booleans and enqueues only a down/up transition when the value changes (`DiscreteInputBuffer.cs:31–45, 52–84`). `RtsInput.OnApplicationFocus(false)` logs focus and calls `ClearTransientInput`; that method clears the queue, suppresses world input, resets selection-mode state and click timing, but does not reset the buffer's physical-state booleans (`RtsInput.cs:32–34`).

Unity Input System's documented default `ResetAndDisableNonBackgroundDevices` soft-resets and disables non-background devices on focus loss, then re-enables and requests synchronization on focus gain. Soft reset returns button controls to default while controls such as pointer position may be excluded; device reset also cancels in-progress InputActions. The fixture overrides this to `BackgroundBehavior.IgnoreFocus` and routes all editor device input to the Game View (`NativeInputFixture.cs:24–31`), so most existing tests do not exercise Unity's real soft-reset path.

## PackageCache verification (project's Input System package)

The project's `Library/PackageCache/com.unity.inputsystem@7a4e1a2a8194` source confirms the relevant 1.20-era ordering. On an editor focus event, the manager first invokes `InputActionState.OnDeviceChange(device, SoftReset)` for enabled devices to cancel in-progress actions, explicitly without changing device state (`InputManager.cs:3567–3587`). The focus handler then processes each device: on focus loss, the reset-and-disable settings disable the device (the disable path performs the soft reset); on focus gain, a previously disabled device is re-enabled and that enable path issues a sync request (`InputManager.cs:3958–4004`). If a device is enabled and the runtime is not running in the background, it requests sync; only a failed sync falls back to `ResetDevice`, whose implementation sends the `SoftReset`/`HardReset` notification before applying the default state (`InputManager.cs:1641–1663`).

This means a successful focus-gain sync is a state event representing the device's current state; a key still physically held can legitimately arrive as `A=true`/`Escape=true`. The project buffer's `Capture` compares that state against its own stale `keyDown[]` value. If it already retained `true`, no new edge is queued. If it retained `false` because the focus-loss soft reset was observed as a state event, the sync of a still-held key would look like a new down edge. The package source does not provide evidence that the buffer's private booleans are reset by `Clear()` or by `onDeviceChange`; this ordering therefore preserves the stale-state hypothesis, while the exact result depends on whether the reset/sync state events reach this subscriber and on the actual held state.

The editor-specific path also matters: when a focus event is seen and game input is not forced regardless of focus, action state is soft-reset before routing decisions; with this project's test override `IgnoreFocus` + `AllDeviceInputAlwaysGoesToGameView`, editor focus events can be early-exited and devices are deliberately left untouched (`InputManager.LegacyFocusHandling.cs:196–211`; `InputManager.cs:3952–3956`). Thus a 032 editor run may fail to produce a focus-gain sync at all, and cannot be treated as proof of the default player reset sequence.

## High-confidence conclusions

1. **A stale-state edge is theoretically possible at the buffer seam, but not established as a bug.** If the buffer saw `A` down, then focus loss clears only queued edges, and the device returns with a down state without an intervening captured up transition, the next physical `A` down compares equal to `keyDown[A]=true` and is ignored. The same shape applies to mouse buttons. Under Unity's documented soft reset, buttons normally reset to default and focus gain requests synchronization, which should produce a state update and clear the remembered booleans; however, whether the queued synthetic/editor events and `OnApplicationFocus` ordering guarantee that in this project is not proven by source alone.
2. **Current FocusPause coverage proves application-level pause and stale-action safety, not fresh-edge delivery after a real device reset.** `FocusPauseTests` verifies repeated focus loss, modal replacement, held train press followed by release, retained selection/group state, and explicit resume (`FocusPauseTests.cs:42–86`). The tests use `IgnoreFocus`, invoke focus loss via `SendMessage`, and do not assert a focus-gained `FRONTIER_FOCUS focused=true` event followed by a fresh keyboard and mouse command. The current 032 negative run also lacks observed focus-gain evidence, so it cannot attribute missed inputs to `DiscreteInputBuffer`.
3. **There is a valid deterministic seam for a minimal falsification test without changing runtime code.** With `inputTrace=true`, queue a key or button down, invoke focus loss, invoke `OnApplicationFocus(true)`, queue the corresponding release, then queue a fresh down after a frame/update boundary. Assert exactly one fresh `Key`/pointer edge reaches the intended action and inspect `FRONTIER_INPUT` timestamps. Repeat with a button held across the loss. Run once with the fixture's `IgnoreFocus` override and once in an actual player/default focus configuration; the latter is needed to test Unity's device soft-reset behavior rather than only the buffer.

## Falsifiable hypotheses and minimal tests

- **H1 (buffer stale boolean):** If no release/state-sync event reaches `Capture` after focus gain, the first fresh press is dropped. Test prediction: `FRONTIER_INPUT` has no new `A down` after the synthetic focus cycle; explicitly queueing a release before the fresh press should make the next press appear.
- **H2 (focus routing/environment):** If the device is still disabled or editor-routed after focus gain, neither the first nor later queued events reach the game. Test prediction: no `FRONTIER_INPUT` events at all until the window regains Game View focus; changing routing/focus while leaving the buffer untouched restores input.
- **H3 (dispatch/UI barrier):** If the edge is captured but consumed or suppressed by `RtsInput` during the pause/modal transition, `FRONTIER_INPUT` will show the event while no command/action follows. Test prediction: a fresh edge appears in trace but the world command is absent; waiting one clean frame after resume should restore the action.

- **H4 (held-key sync edge):** If `Escape` remains physically held across focus loss and the focus-gain sync reports it as down while `keyDown[Escape]` is false, the sync itself can enqueue an Escape down edge and trigger the game's resume/cancel handling. Test prediction: trace shows `FRONTIER_FOCUS focused=true` followed immediately by `FRONTIER_INPUT Key Escape down` without a new user press; releasing Escape then causes the normal up transition. This is a testable risk, not an observed behavior.

The smallest useful artifact is therefore a paired trace of `FRONTIER_FOCUS false`, `FRONTIER_FOCUS true`, `FRONTIER_INPUT` release/down transitions, and the resulting command/action. Without the focus-gain trace or device-state evidence, the observed “no input” remains an environment/focus-routing observation rather than a confirmed `Clear()` defect.

## Minimal package-aware experiment

In a development-only test harness, subscribe to `InputSystem.onDeviceChange` for `SoftReset`, `HardReset`, and `ConfigurationChanged`, enable `inputTrace`, and use the actual player/default background behavior. Queue/hold Escape, trigger focus loss, then regain focus while still holding Escape. Record the ordered stream: device-change notification, `FRONTIER_FOCUS`, any state event captured by the buffer, and resulting `RtsInput` action. Run paired cases with Escape released during the unfocused interval and with it still held. A sync-generated `Escape down` proves H4; no `FRONTIER_INPUT` but later fresh presses working points to stale-buffer or routing differences; no events at all points to focus/editor routing.
