# 0.2.5 输入时序修复记录

本轮依据 0.2.4 独立 macOS 人工对局暴露的问题推进。0.2.4 封存档、客户端和事件证据保持原样；此文件描述 0.2.5 工作工程。尚不能据此宣称阶段 D 完成。

## 观察、假设与验证入口

原生实测中，快速框选后紧接右键曾给旧城镇中心设置集结点；友军覆盖宝箱时，探险家的右键曾成为 Move，清除遮挡后才能 Claim。详见 `Input-Issues-024.md`。

按优先级检查三条可证伪假设：

1. 旧 Update 先处理右键与编队，再处理左键队列，导致命令接收者沿用旧选择。若按真实事件顺序消费，则“框选→右键”和反向“右键→框选”应各自作用于正确接收者。
2. 旧右键和普通快捷键使用帧状态，连续按下/抬起会被折叠，且使用帧末坐标和 Shift。若每条事件携带自己的快照，同帧两次右键应留下两个命令；在两次之间释放 Shift，后者应替换旧队列。
3. 左键选择与右键指令使用同一单位优先 Pick，友军吞掉了宝藏/资源点击。若按指令资格优先匹配交互物，左键仍能选友军，右键能采集/Claim，规则层仍拒绝守卫尚存的宝藏。

执行入口是 Unity Test Runner 的 `Frontier.Tests.OrderedInputTests`。测试使用真实 `InputSystem.QueueStateEvent`、实际 RtsInput、World.Issue 和实体命令队列，单独停止 GameController 的模拟更新以便观察命令；没有暂停 World 来掩盖订单接受失败。

首次旧实现运行 13 项，2 通过、11 失败；细化鼠标保持状态后仍为 2/13。编队测试明确保存了旧城镇中心；旧帧状态入口在这组批量输入中漏掉右键，因此旧测试没有独立复现“已收到右键但选错宝箱目标”的 Move。宝箱错误的旧行为证据来自 0.2.4 原生人工对局，不能把两者混为一次实验。

首次修复运行新旧输入回归 16 项，14 通过、2 失败。审查发现测试夹具的问题：所谓下一次点击没有先释放前一次右键；所谓守卫宝箱误用了第一个无守卫木材宝箱。修正夹具，并保留失败 XML，不将其算作实现通过证据。

## 实现边界

- `DiscreteInputBuffer` 从 Unity Input System 收集左右键边沿与离散快捷键，按到达顺序存入同一个 FIFO。每条记录时间、屏幕位置、Shift 与 Ctrl/Command 编队状态。一个不可分割的硬件状态事件同时改变左右键时，左键边沿先处理；不同事件保留到达顺序。
- RtsInput 在 UI Update 之后的 LateUpdate 处理 FIFO。按钮回调和 ESC 界面切换清空已有队列，保留原有 0.22 秒防穿透窗口。窗口内的新世界指令会被丢弃，这是明确的当前行为，并非零延迟承诺。
- HUD 生产按钮仍保留原来的帧级 Shift 批量训练惯例；每事件修饰键的验证范围是本次重做的世界指令和选择入口。
- 连续镜头平移、缩放和小地图拖动仍随渲染更新。离散世界指令不用帧末鼠标坐标重建。
- 小地图坐标由原生 Canvas RectTransform 映射，左右键也走同一 FIFO，移除第二条 UI 指令回调路径。普通左键定位；A 后左键攻击移动；右键下令。
- 左键保留单位选择优先；右键优先当前可见敌人与适用于选择单位的交互目标，使友军不遮挡资源、宝箱、可施工/修理/驻扎建筑。World 的可见性、守卫、单位资格、资源和人口校验仍是最终规则入口。
- 重开对局和失焦会清除待处理输入与拖动状态。没有据此宣称可进行确定性回放或联网同步。
