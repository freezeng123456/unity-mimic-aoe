## 失焦和输入

本局有三次真实 `focus_lost` 自动暂停，并由 Escape 主动恢复。日志与事件中的暂停前后模拟时刻保持相同：

| 模拟秒 | 暂停持续的真实时间 | 后续证据 |
|---:|---:|---|
| 19.700040 | 57.913709 秒 | 恢复后实际训练村民、采集、探索与建造 |
| 205.703400 | 18.112508 秒 | 恢复后船运到达、时代推进、继续下令 |
| 625.194400 | 101.542110 秒 | 恢复后军事付款、驻扎释放、自然结算 |

这增加了最终 0.2.13 的成功恢复样本，但没有证明所有最小化或桌面切换路径可靠。三次失焦均没有在本局主动执行最小化，具体操作系统焦点转移原因未确定。此前同一最终构建的直接内部可执行文件启动样本在 65.399570 秒暂停后未成功恢复；经 Finder 打开 `.app` 的另一局在 20.100040 秒最小化，窗口恢复后 Escape 与 RESUME 点击也未恢复。两次失败的报告和日志分别保留为 `native-cli-quit` 与 `native-finder-quit`。不能将失败归咎于“只是不规范 CLI 启动”。

桌面抓图多次在 HUD 以下呈白色，而同一客户端新生成的 F9 图能显示正常场景。交付保留一组对照，不能据此宣称屏幕故障已消失，也不能以桌面白图推断 Unity 已停止模拟。F9 只读取本次操作新生成的 PNG，未复用旧帧作为新证据。

0.2.12 临时诊断探针 GUID `276339a26de042219d74a2604d163dfd` 用来定位焦点与设备事件，其结果仅为历史诊断。探针脚本和临时日志组件已从最终 Assets 移除，诊断二进制未作为本轮交付客户端。

## 尚需复现的问题与证据限制

1. **人口显示时序疑点。** 第二座军营已在 678.981262 秒死亡，但 F9 画面在 11:51 和 12:14 仍显示预留 5，12:43 已变为 0。源码死亡路径会释放队列，HUD 每帧读取玩家字段；事件流未保存每次人口字段快照，无法证明是模拟、UI 还是渲染提交时序。保留 `normal-save-barracks-repair`、`normal-release-recover-economy`、`normal-food-repair-recovery`、`normal-redirect-hunters` 四帧；下一轮应使用专用死亡夹具同时观测状态、UI 字符串和最终像素，不能仅凭静态阅读关闭问题。
2. **修理账本精度。** 每模拟步的微小修理成本在 Payment 文案中被四舍五入为 `0 F / 0 W / 0 C`。本局总木支出减四座建筑基础费用 670 W 后为 159.736816 W，与修理存在真实支出一致；仍缺逐事件结构化金额与 HP 增量记录。浮点累计也不能当作逐位精确账本。
3. **本局帧时间只是单个样本。** 客户端报告均值 16.877083 ms、P95 17.481625 ms、托管内存 7,593,984 字节；这不是进程总内存，也没有新增 50/100/200/400 活动单位矩阵、GC 分配率或寻路/战斗分项数据，不能宣称 4K60 或目标规模性能达标。
4. 没有完成声音试听、最终美术/动画、第二文明五时代完整玩家局、新机器安装、签名公证或 Windows/Linux 构建。当前程序化建筑、地面与部分单位视觉仍是开发表现。
